# GUL-405: PR 614 shared-string continuation repair

This repair continues PR #614 from `05f560a46a4320f117d6dc8f95a636fd6b233a11`. It addresses the issue's independent Debug-worker reproduction: a 22,537-byte workbook with 2,000 independent shared strings took 2.84 seconds for the first batch, 9.31 seconds for the second, and exceeded 15 seconds on the third. The production continuation deadline is five seconds. Those are the reviewer's reported baseline observations, not a new local benchmark.

The reader now collects at most 128 cell descriptors, measures the distinct shared references in one string-table scan, and captures only the requested logical byte windows in a second scan. Inline/cache windows are captured by a sequential worksheet replay. Text is assembled in original cell/sheet order. Duplicate, reversed, empty and rich shared strings retain their logical values; no formula, network or embedded content is executed. Long Unicode cells use byte lengths plus scalar-safe windows, without retaining their entire value. Parsers are never reentered. There is no new persistent index, schema, dependency, timeout increase or total-content cap. Prefix replay remains per group and request; very large workbooks have not received broad performance acceptance.

The new representative fixture has 2,000 independent shared strings and reconstructs every output byte through the final row with the real `AskFileReader()` defaults. It restarts the worker after the first response, then separately cancels indexing after the second encoder call, reopens the store, resumes at the committed cursor, and searches the final row. Existing XLSX tests cover shared/inline/cache order, long Unicode, cross-sheet restart, vector reuse, authority/version/cancellation failures and fixed retry behavior. Existing native XLSX readers now use production defaults. Invalid offsets inside shared Unicode and near Int64.max are rejected.
