# GUL-405: mixed PDF page OCR

Based on merged main `f4d549b53679d2b783ac6ce37d1ed8496cb277f1`. A long native finance header previously satisfied the eight-character fast path and hid the raster invoice body. Image-bearing pages now require at least 80 native letters/digits across three body lines, with each line containing at least eight letters/digits and its center within the middle 60% of the crop box. Otherwise the existing local PDFKit/Vision OCR supplements the complete original text. Native-only pages, including short title pages, retain their original fast path. No default timeout, page limit or file quota changes.

Resource discovery reads image/Form dictionaries, including inherited page resources, without decoding pixels. It walks forms iteratively and tracks stream identity to avoid cycles. All PDFKit inspection and Vision work remain in the disposable reader; application startup and migration only inspect recipe strings. This is a text-sufficiency heuristic: inline images are not discovered, unused image resources can cause extra OCR, and an unrelated but sufficient native body can still hide raster text elsewhere. It does not analyze painted image geometry, reconstruct PDF layouts, or add geometric highlighting. Full-page OCR can repeat native headers in the appended text.

The extraction recipe is now `pdf-vision-accurate-auto-2400-image-body-v2`. Completed PDFs with an older recipe are queued again. Same-file-version upgrades preserve vectors only within the existing model/prompt/chunk profile, and adopt exact text/page/offset matches. File replacement or an incompatible profile still discards the old generation. Partial cursors, failed reasons and targeted retry continue to use the existing durable job machinery.
