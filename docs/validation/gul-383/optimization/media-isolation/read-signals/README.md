# GUL-405: media helper startup and I/O scheduling

The media helper used process-level background QoS, unlike the utility text indexer. This also restricts dyld and file I/O before Swift or the model loader can make progress. The product change selects utility for indexing helpers; the existing one-thread CPU configuration, SIGSTOP/SIGCONT work budget, pressure/thermal interruption, ownership, cancellation and timeouts remain in force. Foreground queries retain their existing priority.

Apple documents background disk-I/O throttling in [Dispatch's background-priority documentation](https://developer.apple.com/documentation/dispatch/dispatch_queue_priority_background?language=objc). That is the scheduling mechanism relevant to this fix, not a diagnosis of hardware, memory pressure or one stuck read. The local comparison supports the launch-policy correction; it is not a kernel I/O trace or a broad performance benchmark.

The opt-in C observer interposes file reads and signals in a disposable diagnostic run. It writes numeric events to a precreated current-user mode-0600 mmap file. No model strings, paths, request text, pixels or user files are recorded. Reads are dense for the first 256 calls, periodic every 1,024 calls, and retained on slow completion. Every retained completion carries its own entry timestamp. Cumulative bytes include rereads and are not file offsets. Exact helper PID/start identity, signal return and observed Darwin process state are recorded. Tracing does not alter the signal target or return value; errno is preserved.

An initial test caught a clock mismatch: Darwin CLOCK_MONOTONIC did not match the existing probe/Python clock. The observer now uses mach_absolute_time and verifies the common clock against a real child. The first screenshot attempt captured signals but missed reads because the native archive bypassed ordinary fopen. The lazy fread classifier was verified through fdopen. A second baseline then stalled before its observer constructor or first Swift stage, so it supplies no GGUF-read attribution. Both failed observations remain in `../stage-budget/read-signals-once` and `read-signals-correlated`, with hash-matched observer source snapshots retained here.

The second baseline's media PID had **461 successful stop/resume pairs**, one unchanged start identity and no failed/unpaired signal. Its commanded stop intervals total **18.9395 s** during an approximately 39.28 s request. The remaining wall time is not CPU time. The absence of the initial constructor and tiny sampled CPU/RSS locate this observation before model parsing; it cannot be called a GGUF read timeout. The preceding baseline did reach the loader, whose model phase took 17.8528 s, but lacked read events.

The declared comparison changes only background spawn QoS to utility using an explicit observer option, retaining the actual production budget and 40 s probe/60 s parent limits. The third observation (`read-signals-utility`) generated a valid normalized **768-dimensional visual vector**, indexed it alongside one OCR text vector and completed the image job in **28.062 s**; the full driver took **30.218 s**. Model/context/projector phases took **0.9618 / 0.0021 / 0.4814 s**. The media PID still had **203 successful stop/resume pairs**, totaling **8.2009 s**. There were 2,431 retained read completions and no dropped/incomplete events. A 40.099 ms read overlapped a 40.074 ms commanded stop interval; its 25.8 microseconds of remaining wall time is not a CPU measurement. The original reports' `complete` field meant indexing only; they did not execute successful queries.

The corrected standalone probe checks readiness before pausing background work, imposes the original cutoff on its service query, and reopens SQLite using the real captured query vector. It requires visual `image` evidence and exact `image-ocr` error-code evidence before declaring screenshot retrieval complete. Its fixed visual query was chosen after inspecting the synthetic fixture and before execution: `black text on a white background` has no overlap with the OCR text. It does not supply fake embeddings. Diagnostic wrappers delegate to the actual service, worker, model verifier, extractor and store; controlled idle/access inputs and Debug instrumentation remain disclosed. This is service-to-result validation, not a native UI latency test or a recall benchmark.
