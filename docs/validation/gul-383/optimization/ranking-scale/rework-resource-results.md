The prior resource experiment is retained separately in `resource-after-rework`; it used a different workload and an earlier probe, so it is not a causal before/after estimate of this final implementation.

Each phase received 120 actual files, four every 30 seconds: a text document, generated PNG, speech WAV and MOV. The first document is 3,840,014 bytes, followed by 29 shorter documents. The four media/text templates are reused; this is a sustained controlled workload, not the user's representative 27,000-file corpus. The MOV has video frames but no audio. Actual extraction and embedding run through production workers. No SQL repeated-chunk scale fixture is used in this resource comparison.

The independent AppKit probe posts generated keyboard/mouse/window-resize events only to its own process. ScreenCaptureKit reads only that window's generated event-ID bars and matches exact IDs with WindowServer display timestamps. Every formal input matched both a handler and a displayed frame: 902/902 per condition. There were no missing events, occluded/hidden handler windows, injected calibration stalls or substituted zero presentation values. The producer's maximum delay was 1.134/1.128 ms OFF/ON. A deliberate calibration stall separately demonstrated that the producer remains independent while delayed/missing displayed events are retained. `CAMetalDrawable.presentedTime` was zero; it remains null. The WindowServer observation is not physical HID latency, monitor scanout or the search result's compositor timestamp. `analyze_final_resource.py` derives adjacent-sample CPU, physical IO, memory, GPU, thermal and input statistics. Observed CPU totals are 14.18/378.20 seconds OFF/ON, averaging 1.57/41.88% of **one core** over each phase. These are lower bounds: initial/final intervals and a process entirely between two samples are missed. Lifetime `ps %CPU` is retained raw but never used as instantaneous CPU. On this host the libproc CPU counters required Mach-time conversion; the corrected sampler was cross-checked against `process_time_ns`, and the first failed calibration is retained. Rusage reads were available for every sampled owned process. System XPC/decoder services outside the owned process tree are not attributed to the application; this is not a complete machine CPU account. Physical IO is likewise an observed lower bound, not logical bytes extracted or an exact total including all child exits.

The response probe itself wrote about 57.29 MiB. The report separates these processes; probe overhead is present in both conditions. Memory pressure stayed nominal (`kern.memorystatus_vm_pressure_level=1`); sampled application thermal state was nominal (0). `pmset` reported no recorded thermal/performance warning, which is not a temperature or watts measurement. Swap use fell from 4679.31 to 4671.31 MiB OFF and 4671.31 to 4663.31 MiB ON. There was no measured swap growth. Available IOAccelerator utilization and memory counters are global, not per-PID GPU work or energy: GPU utilization p50/p95 was 1/1% in both phases, max 12/8%. Privileged power/temperature metrics were not available and are not invented.

At ON completion, 672 chunks were published but only **309 had vectors**, with 363 pending vectors. There were 32 completed jobs, 26 partial jobs and no failed jobs. Published file counters include partially processed documents: 28 documents, 10 images, 10 audio and nine videos must not be described as 57 completed files. The 3.84 MB document remained partial while media continued advancing. Queues retained 27 documents, 20 images, 20 audio and 21 videos. Effective measured throughput was about 0.342 encoded vectors/s and 0.0354 completed jobs/s over the full phase. The backlog grew under this arrival rate; this is not a throughput-acceptance claim or an improvement comparison with the earlier, shorter-text workload. Read-only numeric DB observations show continued document/media progress, without collecting paths or contents.

The defaults are expressed as time quanta, not promised machine CPU percentages: 40 ms work / 40 ms rest at idle, 10/90 ms for activity, low power or warning pressure, immediate interruption/resource release on priority or severe pressure/thermal signals, and five seconds of clear state before pressure recovery. The pinned CPU reference measured text/image/audio medians of 303.26/3244.98/448.94 ms versus GPU 32.73/201.20/50.10 ms; this supported a single CPU thread and four document checkpoints before yielding to media. The sustained run confirms continuing work and an observed idle duty rate on this host. Active-user and adverse-pressure behavior are covered deterministically, not established by this nominal-pressure run. These defaults still need resource/interaction acceptance: lowering CPU alone has not eliminated the observed input tail, and the backlog is material.
