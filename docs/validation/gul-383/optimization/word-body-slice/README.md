# GUL-405: Word DOCX body slice

Partial delivery from main `29e4817385eba9ae3522bf50334a58885eaeb4de`, including merged PR #595. GUL-405 remains in progress; GUL-406 stays parked. RTF/HTML were assessed against the local-only import requirement and are left for the next short segment. The existing `AskLocalWebTools.htmlText` performs offline HTML-to-text conversion on an entire String; it needs a bounded continuation adapter before semantic indexing can reuse it safely. RTF currently has an exporter, not an indexed-content reader. This slice adds no package dependency: the macOS SDK already supplies the `zlib` module used here.

DOCX main-body text now uses the existing disposable file reader, descriptor identity/version checks, deadlines, 32 KiB content batches, durable jobs, lexical publication and vector queue. The ZIP reader handles stored/deflated ZIP32 entries, validates member names/headers, sizes and final CRC, and streams only `word/document.xml`. It never unpacks a path, opens a relationship, executes a field, loads an external resource or uploads content. XML DTDs/entities requiring declarations and NUL-containing XML are rejected before XML parsing; ordinary built-in XML entities remain supported. Paragraphs, tables, tabs, line breaks, split runs, Chinese, Unicode and CDATA are covered. Deleted text and field instructions are excluded. Offsets describe UTF-8 bytes in the extracted logical body; no Word page number or external-reader jump is fabricated.

The format list is now part of completed and interrupted discovery keys. Upgrading therefore revisits previously scanned folders and enqueues DOCX without deleting the database or asking for a rebuild. Compatible existing text/PDF vectors and their recipes are retained. New DOCX jobs carry a separate recipe. Discovery itself repeats once after the upgrade, so a very large existing folder catalog still has a scan cost; it does not imply global re-encoding.

Corrupt content retains `unreadable-content`, ZIP encryption retains `password-required`, and unsupported encodings/archive variants retain `unsupported-document`. Standard Office password encryption uses an OLE compound container rather than ordinary ZIP; this slice reports that container as unsupported instead of claiming to decrypt it. ZIP64, unsupported ZIP compression, headers/footnotes in other package members, legacy DOC/XLS/PPT, XLSX/PPTX and ODT remain unsupported. There is no file/chunk total quota. Resuming a DOCX logical cursor replays decompression/parsing of its prefix in the disposable reader, but does not encode committed chunks again; very large compressed bodies may hit the existing reader deadline. Persistent decompressor state and faster random continuation remain unverified.

Self-review traced reader → bounded body chunks → durable FTS/cursor → compatible vectors → query evidence, plus cancellation, generation/version checks, permission changes, retries, memory/descriptor ownership, SQL parameter binding, migration and documentation. It corrected both discovery key paths and restricted PDF vector adoption to PDFs before validation. The initial dependency-preparation build overlapped source edits and was rejected by Swift. Next short segments retain: RTF/HTML, XLSX/PPTX/ODT and explicit legacy Office handling; mixed scanned/native PDF OCR and screenshot OCR/geometry; overlapping/silence-aware audio and resumable deduplicated video sampling; location-aware opening from both entries; per-category progress/partial/failure retry; Range/ETag/checksum download recovery. Rollback can revert this slice or disable the existing experiment. A revert also changes the discovery key and causes a scoped rescan. The database remains additive; unsupported DOCX entries can be pruned by normal discovery, with no destructive database migration. Existing ranking, model profile, privacy scope, feature defaults and voice priority are unchanged.
