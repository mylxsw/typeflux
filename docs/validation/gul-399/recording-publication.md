## Behavior and ownership

`ScreenRecordingFiles.preparePublication` prepares a bounded same-directory staging file off MainActor. `ScreenRecordingPublication.commit` then checks the original generated-file revision, pinned destination directory, staging revision and expected existing target. It records a committing receipt, rechecks the original coordinator source/session/permission epoch/action generation, and performs one descriptor-relative rename with no suspension after authorization. New targets use `RENAME_EXCL`; explicitly selected existing files retain replacement semantics. Default naming still chooses a numbered collision-free filename before commit. A concurrent late collision fails without retrying the rename or encoder.

Preparation has two admission slots acquired before detached work, an 8 GiB regular local/resident source limit, 4 KiB source/destination path limits, a 64 KiB streaming copy buffer, a 0600 staging file, a 1024-entry bounded source-directory scan, and at most 16 retained publication receipt entries per session. New recording sessions are 0700. The descriptor actually opened for copying must match device/inode/size/mtime/ctime, including nanoseconds; final source checks reject later changes. Slots stay occupied until uncooperative host work actually returns and the prepared publication is released. There is no queue, application-lifetime cache or new worker executable.

Each attempt has a fresh UUID and bounded (8 KiB) private JSON receipt beside its generated output. Preparing/prepared/committing/published/unknown/cancelled states preserve what is known; committing after a crash must be treated as uncertain, not permission to retry. Before/after-effect injected rename failures both retain the receipt and original/generated bytes. An uncertain rename also retains any remaining hidden destination staging file. Known successful rename is not undone if receipt acknowledgement persistence fails. Receipts are not a global durable replay service: an ordinary fully successful session can still be cleaned up, while sessions containing earlier partial/failed/uncertain attempts are retained. No automatic retry, rollback or original deletion follows a preparation/encoding/publication error. Explicit confirmed discard remains explicit discard.

The coordinator admits at most two exports, rejects duplicate clicks per owner, retains admission through uncooperative cancellation, snapshots the original source before encoding, and fences late completion on source revision, generation, original permission epoch, account/window retirement and owner release. The large copy is asynchronous; commit and callback authorization have no intervening await. Progress callbacks update one locked latest finite monotonic value; one owned 200 ms monitor updates UI, rather than creating one MainActor task per callback. A successful later export preserves earlier failed outputs and their original recording. Native encoder/coordinator failure paths no longer remove a generated candidate. Five languages explain unavailable and unknown publication outcomes.

## Remaining boundaries and next step

The original native AVAssetExportSession/composition and detached GIF ImageIO/AVAssetImageGenerator work remains in the host. This increment bounds admission and publication staging, **not native encoding output allocations/disk usage/time before preparation**. Its 8 GiB output rejection can occur after the native encoder already wrote a larger candidate. Next isolate that encoder into the existing media helper while preserving trim, transform, all-track mixing and GIF contracts, then connect its owned output to this prepare/commit boundary without replay.

Filesystem checks/copy/rename/receipt writes can block; even small descriptor operations on MainActor are not a hard latency guarantee. Two prepared copies may occupy 16 GiB in addition to original/native candidates and playback/timeline/poster copies. Retained failed sessions/staging consume disk until explicit cleanup; there is no new receipt browser, automatic reconciliation or eviction. Metadata checks are not immutable transactions. Another unsandboxed process can mutate files between checks; explicit replacement is not a filesystem compare-and-swap. A rename already authorized/dispatched can finish despite subsequent external changes. The no-await authorization boundary serializes application revocation on MainActor, not arbitrary OS activity. No fsync/power-loss durability, rollback, zero-effect-after-dispatch, system-wide OOM or arbitrary host-crash guarantee.

All remaining approved stage-2 adapters, lifecycle/persisted-health integration, native/media paths and audio/TCC/signing/performance work remain. File export does not decide microphone/capture ownership. GUL-399 stays **in_progress**.
