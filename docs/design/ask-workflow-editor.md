# 随便问：工作流编辑器设计方案

> 状态：设计，待确认。配套设计稿：`docs/design/ask-workflow-editor.html`（`?solo=<id>` 单独看一屏，`?light=1` 看浅色），截图在 `docs/design/ask-workflow-editor/`：`1-overview.png` 总览、`2-keywords-input.png` 关键字和输入、`3-output.png` 输出、`4-failure.png` 测试失败、`5-json.png` 清单视图、`6-external-change.png` 外部修改、`7-new.png` 新建、`8-entry.png` 入口、`9-light.png` 浅色。
> 基于已经上线的 W1（`docs/design/ask-launcher-workflows.md` 第 12 节）。本方案只改「怎么编辑」，不改工作流包格式、运行器和安全模型。

## 0. 一页结论

1. **现在的问题。** W1 里编辑工作流只能「在编辑器中打开」：用文本编辑器同时打开 `workflow.json` 和脚本。用户要记清单字段名和取值，改错了只能回到设置里看一行红字；没法试运行，只能打开启动器真跑；而且在外部改完文件，哈希变了，工作流被标成「已修改」，还得再点一次「检查并信任」——用户改自己的工作流也要反复确认。
2. **做一个独立的「工作流编辑器」窗口**（截图 1）：
   - 左边：所有工作流和当前工作流的文件。
   - 上方：**流程条**，关键字 → 输入 → 脚本 → 输出，每一步显示当前配置的摘要，点哪一步编辑哪一步，有问题的步骤带红点。
   - 中间：按步骤编辑。关键字、输入、输出是表单；脚本是内置代码编辑区（行号、着色、查找）。
   - 右边：**测试运行**，和启动器用同一个运行器，预览区就是启动器里的卡片。
3. **表单和 `workflow.json` 双向同步**（截图 2、5）。表单只改它认识的字段，清单里的其他字段原样保留；JSON 视图把校验错误标到对应的行。
4. **出错直接定位到行**（截图 4）。从 stderr 里识别「文件 + 行号」，标在代码上；启动器的错误卡片加 **⌘E 编辑工作流**，直接打开编辑器到出错的那一行。
5. **信任不打折扣**（截图 6）。在编辑器里保存会自动更新信任，前提是这段时间里没有别人改过文件；只要有外部修改，就必须先看差异、确认信任。编辑器不能变成绕过信任的后门。
6. **不加新依赖。** 代码区用 `NSTextView` 加一个轻量的着色器，查找用系统自带的查找栏。
7. **分两步做。** E1：窗口、流程条、表单、代码区、校验、保存和信任、测试运行（文本 / 不输出）、新建、入口。E2 跟着 W2：条目列表的预览、边打边出、钥匙串密钥、运行记录面板。

## 1. 用户怎么用

### 1.1 改一个已有的工作流

设置 → Agent → 内置工具 →「启动器工作流」，点一行的「编辑」，打开编辑器。

1. 在流程条上点「脚本」，改代码；文件标签上出现未保存的圆点。
2. 在右侧输入 `100 usd jpy`，按 ⌘R：先保存，再运行，右侧显示启动器里的样子。
3. 出错时，出错的行标红，stderr 里的 `main.py, line 12` 可以点。改完再 ⌘R。
4. 关掉窗口。保存过的修改立即生效，不需要再确认信任。

### 1.2 新建一个工作流

「＋ 新建」→ 选模板（Python / Node / zsh 输出文本，zsh 只做事，空白，复制现有）→ 填名称和关键字（实时查重）→「创建并编辑」（截图 7）。

### 1.3 在启动器里遇到错误

工作流出错时，错误卡片显示 stderr 末尾和 **⌘E 编辑工作流**。按 ⌘E，启动器关闭，编辑器打开到这个工作流、出错的那一行（截图 8）。

## 2. 窗口结构

```
┌ 工具栏：图标 名称 id·版本 [运行时] [状态]        未保存· [保存 ⌘S] [▶ 测试运行 ⌘R] ··· [开关] ┐
├────────────┬────────────────────────────────────────────┬─────────────────┤
│ 搜索        │ 流程条：[关键字] → [输入] → [脚本] → [输出]         │ 测试运行          │
│ 工作流列表   ├────────────────────────────────────────────┤ 输入 / 示例选中文字 │
│  └ 文件     │ 标签：表单 | workflow.json  或  main.py | …      │ 预览 stdout stderr │
│            │ 编辑区                                       │ 传入了什么        │
│ ＋新建 导入  ├────────────────────────────────────────────┤ 最近运行          │
│            │ 状态栏：问题 · 解释器 · 行列 · 编码              │                 │
└────────────┴────────────────────────────────────────────┴─────────────────┘
```

- **单独的窗口**，只有一个实例；从任何入口打开都复用它，切到对应的工作流。默认 1220×700，最小 960×560；右侧测试面板可以收起（⌥⌘T）。
- **左栏**：全部工作流（状态点：绿=可以运行，黄=需要确认，红=清单有误，灰=已停用），选中的展开文件列表：「配置」（`workflow.json`）、脚本、其他文本文件。二进制文件（图标）只显示不打开。
- **工具栏**：名称、`id · 版本`、运行时、状态；保存、测试运行、更多（在 Finder 中显示、用外部编辑器打开、复制、删除）、启用开关。
- **状态栏**：问题数（点击跳到第一个问题）、解释器路径、光标位置、编码和缩进。
- 切换工作流或关窗口时有未保存的修改，弹出「保存 / 不保存 / 取消」。

## 3. 流程条和各步骤

流程条就是工作流做的四件事。每个节点显示摘要，选中的节点高亮，对应的校验问题让节点带红点（问题按字段前缀归到步骤：`keywords*` → 关键字，`input*` → 输入，`command*` → 脚本，`output`/`run*`/`env` → 输出）。

| 步骤 | 摘要 | 编辑区 |
|---|---|---|
| 关键字 | 关键字标签 + 第一个显示名称 | 表格：关键字、显示名称、预设参数（键值对），可增删、拖动排序。输入时就查重（和内置插件、其他工作流同一个命名空间，复用 `AskKeywordMatcher.problem` 和 `AskWorkflowStore.keywords(of:excluding:)`），错误写在那一行下面。 |
| 输入 | 「可选 · 或选中文字」 | 参数：必填 / 可选 / 不需要；选中的文字：没参数时用 / 总是带上 / 不要；**参数模板**：一格一个 argv，占位符 `{query}` `{selection}` `{option:名字}` 点一下插入，名字从关键字表的预设参数里取。下面实时显示示例的 argv 和 stdin JSON（复用 `AskWorkflowManifest.arguments` 和 `AskWorkflowPlugin.stdin`）。 |
| 脚本 | `main.py {query}` | 代码区（第 4 节）。脚本 / 内联脚本切换（只有 zsh、bash 可以内联）。 |
| 输出 | 「文本 · 10 秒」 | 输出：文本 / 不输出 / 自动 / 条目列表（W2）；运行：按 ↩ / 边打边出（W2）；超时（1–300 秒）；运行时和解释器（自动找到的路径以占位文字显示，找不到时提示怎么安装）；环境变量表。右边按当前选择渲染启动器预览。 |

W2 才支持的选项（条目列表、边打边出）显示为不可选并标「W2」，和现有校验一致。

## 4. 代码区

- `NSTextView`（TextKit 1，`NSScrollView` + 行号 `NSRulerView`），等宽字体，关闭智能引号、自动替换、拼写检查，`isRichText = false`。
- **着色**：每种运行时一组正则（注释、字符串、关键字、数字、函数调用），只给可见范围和编辑过的段落重新着色；超过 2,000 行或 256 KB 时只着色可见范围。语言按运行时和扩展名决定（`.py` `.js/.mjs` `.ts` `.sh/.zsh` `.applescript/.scpt` 文本、`.json`）。不引入 tree-sitter 等依赖。
- **编辑**：Tab 插入 4 个空格（按文件里已有的缩进自动判断 2 或 4），回车保持缩进，⌘/ 注释，撤销重做，⌘F 用系统查找栏（`usesFindBar`）。
- **问题标记**：行号栏的红点 + 该行下方一行说明（截图 4、5），来源有两个：清单校验（只在 `workflow.json` 里）和最近一次测试运行的 stderr。
- 只打开 UTF-8 文本文件，最大 1 MB；更大或不是 UTF-8 的文件提示「用外部编辑器打开」。
- 「用外部编辑器打开」保留，仍然用纯文本编辑器打开（不会误运行脚本）。

## 5. 表单和 `workflow.json` 同步

- 编辑器持有一份**草稿**：清单的原始 JSON 对象（`[String: Any]`，保留全部字段）+ 由它解码出的 `AskWorkflowManifest`。
- 表单修改时，只改原始对象里对应的键，再重新解码、校验；所以清单里表单不认识的字段（作者自己加的 `x-roots`、以后的新字段）不会丢。写出时用排序键、两空格缩进，和模板一致。
- JSON 视图修改时（停顿 300 ms 后）解析：能解析就刷新表单；解析不了时只标语法错误位置，表单变为只读，直到 JSON 恢复正确。
- 校验复用 `AskWorkflowManifest.problems(in:)`，再加上 JSON 解码错误（`AskWorkflow.describe`）。每个问题带字段路径，JSON 视图用路径找到对应的行（简单的键路径扫描，不需要完整的 JSON 位置解析器）。
- 能猜到的给一键修正：`command.script` 找不到时，列出文件夹里同扩展名或同运行时的文件。

## 6. 保存、信任和外部修改

这是本方案里最需要小心的部分：编辑器会写文件，也会更新信任。

### 6.1 保存

- ⌘S 保存全部修改过的文件；每个文件先写临时文件再原子替换（`replaceItemAt`），脚本保留原来的权限，新建的脚本设为 `0755`。
- **有校验问题也允许保存**：写了一半的工作流在启动器里显示「清单有误」，和今天一致。
- 保存后重新计算内容哈希，刷新 `AskWorkflowStore`。

### 6.2 保存时什么时候更新信任

编辑器打开一个工作流时，记录**载入时的哈希** `H0` 和它当时的状态。保存时：

| 情况 | 结果 |
|---|---|
| 载入时是「可以运行」，并且保存前磁盘上的哈希仍然是 `H0` | 写入，记录新哈希为已信任。用户自己改的，不需要再确认。 |
| 载入时是「已停用」，同上 | 写入，更新信任，仍保持停用。 |
| 载入时是「未信任」或「已修改」 | 写入，**不**更新信任。工具栏仍显示「检查并信任…」。 |
| 保存前磁盘上的哈希已经不是 `H0`（编辑器外有人改过） | 不写入，出现外部修改横幅（6.3）。 |

「检查前后哈希 + 写入 + 记录信任」在主线程上一次完成，中间不让出；写入后立刻重新计算哈希，记录的是磁盘上真实的哈希，而不是我们以为写进去的内容。

### 6.3 外部修改

- 编辑器监听当前工作流文件夹（`DispatchSource` 文件系统事件，防抖 300 ms，重新计算哈希）。
- **没有未保存的修改**：外部改动直接载入。如果工作流原来是「可以运行」，现在会变成「已修改」——编辑器里出现横幅，和启动器一样，确认信任前不能运行。
- **有未保存的修改**：横幅「main.py 在编辑器外被修改了」，三个选择（截图 6）：
  - 「查看差异并信任…」：逐文件显示差异（我的版本 / 差异 / 外部版本），确认后走现有的信任面板。
  - 「载入外部版本」：丢掉自己的修改。
  - 「保留我的版本」：覆盖外部改动；保存后**不**自动信任，因为外部改动可能已经被运行过或者还在别的文件里——工作流保持「已修改」，需要用户点信任。
- 测试运行和启动器一样先检查信任：不是「可以运行」时，测试按钮不可用，提示「先检查并信任」。

## 7. 测试运行

- **⌘R 先保存再运行**。这样测试的就是磁盘上的那一份，和启动器完全一致，信任检查也不需要特殊处理。
- 输入：关键字（多个关键字时可以选，用于带上预设参数）、参数、可选的「示例选中文字」、可选的「来源 App」（默认 Typeflux 自己）。
- 运行：直接调 `AskWorkflowPlugin` 的同一套路径（`input(for:)`、`invocation`、`environment`、`AskWorkflowRunner`），所以超时、输出上限、干净环境、取消时结束进程组全部一样。stdin 里的 `reason` 用 `submit`，脚本看不出是测试——我们希望行为一致。
- 结果标签：
  - **预览**：按清单的输出类型渲染启动器卡片（文本 / 「启动器会关闭」/ 错误卡片）。
  - **stdout**、**stderr**：原样，stderr 里识别出的位置可以点。
  - **传入了什么**：实际的 argv、环境变量（只列 `TYPEFLUX_*` 和清单的 `env`；密钥打码）和 stdin JSON。
- 运行中按钮变成「停止」（⌘.）；运行中再按 ⌘R 会先结束上一次。
- 测试运行也写进 `AskWorkflowLog`（标记来源是测试），「最近运行」里能看到启动器和测试两种。日志仍然**不记录输入输出**；测试面板里显示的输出只在内存里，关窗口就没了。

### 7.1 从 stderr 找行号

只认指向**工作流文件夹里的文件**的位置，避免把第三方库的堆栈标到用户的代码上：

| 运行时 | 格式 |
|---|---|
| Python | `File "…/main.py", line 12` |
| Node / TypeScript | `…/main.js:12:5`、`at … (…/index.ts:12:5)` |
| zsh / bash | `main.sh:12:`、`main.sh: line 12:` |
| osascript | `main.applescript: 1:20: execution error` |

取最后一个匹配的位置（最靠近出错点），在那一行下面显示 stderr 的最后一行。

## 8. 入口

- **设置列表**：每行加「编辑」按钮；清单有误时变成「修复…」，打开后跳到第一个问题。「用外部编辑器打开」移到 ··· 菜单。列表底部加「打开工作流编辑器」。
- **新建**：「＋ 新建工作流…」打开编辑器并弹出新建面板。
- **启动器**：工作流的结果卡片支持 ⌘E（成功时也可以用）：关闭启动器，打开编辑器到这个工作流；出错时直接到出错的行。快捷键说明写在卡片按钮和底栏里。
- 不放进菜单栏菜单，避免增加一个很少用到的入口。

## 9. 新建工作流

- 模板：现有的 4 个（`AskWorkflowTemplate`）+「空白」（只有清单，运行时和脚本自己选）+「复制现有工作流」（复制文件夹，id 和关键字自动加后缀）。
- 先填**名称**和**关键字**（实时查重）；ID 由名称生成（`local.` + 名称转成的 slug：中文用系统的 `CFStringTransform` 转拼音，转不出时用模板 slug），可以手改，用 `AskWorkflowManifest.isValidID` 校验。
- 创建后视为已信任（和今天一样，用户自己创建的），直接进入编辑器的「脚本」步骤。
- 导入文件夹 / `.typefluxworkflow` 也从这里进入（导入属于 W3）；导入的工作流先走信任面板，再进编辑器。

## 10. 代码结构

新文件放在 `Sources/Typeflux/Ask/QuickResults/Plugins/Workflow/Editor/`（模型）和 `Sources/Typeflux/Settings/WorkflowEditor/`（界面）。

| 类型 | 职责 |
|---|---|
| `AskWorkflowDraft` | 草稿：原始 JSON 对象、解码出的清单、打开的文件内容、修改标记；`set(_:at:)` 按键路径改原始对象；`problems` 合并解码错误和清单校验；`step(for:)` 把字段路径归到流程步骤。纯值类型，便于测试。 |
| `AskWorkflowDraftWriter` | 原子写入、权限、新文件；返回写入后的哈希。 |
| `AskWorkflowEditorModel`（`@MainActor ObservableObject`） | 当前工作流、草稿、`H0`、选中的步骤和文件、保存（第 6.2 节的规则）、外部修改监听和冲突状态、新建和复制。 |
| `AskWorkflowTestRun` | 用 `AskWorkflowPlugin` 和 `AskWorkflowRunner` 跑一次，收集 stdout / stderr / 退出码 / 耗时 / 实际传入的内容；可取消。 |
| `AskWorkflowStderrLocator` | 第 7.1 节的行号识别。 |
| `AskWorkflowSyntaxHighlighter` | 按语言的正则着色，输入字符串和范围，输出着色区间（不依赖 AppKit，便于测试）。 |
| `AskWorkflowEditorWindowController` | 单实例窗口，`open(workflowID:line:)`。 |
| `AskWorkflowEditorView` + `AskWorkflowFlowStrip` + 各步骤的表单视图 + `AskWorkflowCodeView`（`NSViewRepresentable`） | 界面。 |

需要改的现有代码：

- `AskWorkflowStore`：加 `save(_ draft:, expectedHash:)`（第 6.2 节的规则放在这里，编辑器和以后的 AI 生成共用）、`duplicate(_:)`、空白模板。
- `AskWorkflowLog.Entry`：加 `source`（启动器 / 测试）。
- `AskWorkflowSettingsView`：「编辑」「修复…」按钮、菜单项、「打开工作流编辑器」。
- 工作流的结果卡片：加 ⌘E 动作（`AskPluginAction` 新增 `editWorkflow(id:line:)`，只对工作流插件出现）。
- 本地化字符串（中英文）。

## 11. 测试

- **草稿**：按键路径修改不丢未知字段；表单 ↔ JSON 往返一致；JSON 语法错误时表单只读；字段路径归到正确的步骤。
- **保存和信任**（第 6.2 节每一行一个用例）：可以运行 → 保存后仍然可以运行；未信任 / 已修改 → 保存后仍然需要确认；保存前文件被外部改过 → 不写入、报告冲突；「保留我的版本」覆盖后不自动信任；写入后记录的是磁盘上的真实哈希。
- **原子写入**：保留脚本权限；写入失败时原文件不变。
- **外部修改**：无未保存修改时自动载入；有未保存修改时进入冲突状态。
- **测试运行**（真实进程，用仓库内的夹具脚本）：和启动器同样的 argv / 环境 / stdin；超时和停止后没有残留进程；不信任时不能运行；密钥在「传入了什么」里打码；日志不含输入输出。
- **行号识别**：四种运行时的格式；只认工作流文件夹里的文件；多个匹配取最后一个。
- **着色器**：每种语言的注释、字符串（包括转义引号和多行字符串）、关键字；大文件只处理给定范围。
- **新建**：名称生成 ID、关键字查重、复制工作流加后缀。
- **界面**：截图测试覆盖设计稿的各个状态；启动器错误卡片 ⌘E 打开编辑器并定位到行。
- 新代码覆盖率 ≥ 90%。

## 12. 里程碑

| 阶段 | 内容 |
|---|---|
| E1 | 编辑器窗口、左栏、流程条、关键字 / 输入 / 输出表单、`workflow.json` 视图和同步、代码区（着色、行号、查找、缩进）、校验和问题定位、保存和信任规则、外部修改和差异、测试运行（文本 / 不输出）、stderr 行号、新建面板（含空白和复制）、设置和启动器入口。 |
| E2（随 W2） | 条目列表的预览和测试、边打边出（测试面板里边打边出地跑）、钥匙串密钥的编辑（只写不读）、运行记录面板的完整版。 |
| 以后（随 W3） | 让 AI 写工作流：描述需求，生成清单和脚本写进草稿，用差异视图确认后保存，同样不自动信任外部来源的内容；导入导出。 |

## 13. 需要你确认

1. **保持「一个工作流 = 一个脚本」**，流程条只是把它的四个环节可视化。还是希望做成 Alfred 那样的**多节点连线**（一个工作流里串多个脚本、条件分支）？我建议先不做：现有清单、运行器、信任都是按单脚本设计的，多节点会让格式和安全模型都复杂很多；串联需求可以先在一个脚本里完成。
2. **独立窗口**，而不是在设置页里展开。设置窗口太窄，放不下代码和测试面板。
3. **⌘R 先保存再运行**。另一种做法是把草稿复制到临时目录去跑，不碰原文件；但那样测试的不是启动器会运行的那一份，信任检查也要另做一套。
4. **代码区用 `NSTextView` + 正则着色**，不引入 tree-sitter 或在 WebView 里放 Monaco。够用、没有新依赖、包体不变；代价是着色不如真正的语法分析准确，复杂编辑仍然建议用外部编辑器。
5. **在编辑器里保存自动更新信任**（第 6.2 节的条件）。这是解决「改自己的工作流还要反复确认」的关键，同时保证外部改动一定要人看过。
