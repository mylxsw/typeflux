# 随便问：工作流编辑器设计方案

> 状态：E1（编辑器）和 E2（AI 助手）已实现，实现说明见第 15 节；E3 随 W2。配套设计稿：`docs/design/ask-workflow-editor.html`（`?solo=<id>` 单独看一屏，`?light=1` 看浅色），截图在 `docs/design/ask-workflow-editor/`：`1-overview.png` 总览、`2-keywords-input.png` 关键字和输入、`3-output.png` 输出、`4-failure.png` 测试失败、`5-json.png` 清单视图、`6-external-change.png` 外部修改、`7-new.png` 新建、`8-entry.png` 入口、`9-light.png` 浅色、`10-ai-generate.png` AI 一键生成、`11-ai-assistant.png` AI 修改提案、`12-ai-fix.png` AI 修复和风险暂停。
> 基于已经上线的 W1（`docs/design/ask-launcher-workflows.md` 第 12 节）。本方案只改「怎么编辑」（包括让 AI 来写），不改工作流包格式、运行器和信任模型。

## 0. 一页结论

1. **现在的问题。** W1 里编辑工作流只能「在编辑器中打开」：用文本编辑器同时打开 `workflow.json` 和脚本。用户要记清单字段名和取值，改错了只能回到设置里看一行红字；没法试运行，只能打开启动器真跑；而且在外部改完文件，哈希变了，工作流被标成「已修改」，还得再点一次「检查并信任」——用户改自己的工作流也要反复确认。
2. **做一个独立的「工作流编辑器」窗口**（截图 1）：
   - 左边：所有工作流和当前工作流的文件。
   - 上方：**流程条**，关键字 → 输入 → 脚本 → 输出，每一步显示当前配置的摘要，点哪一步编辑哪一步，有问题的步骤带红点。
   - 中间：按步骤编辑。关键字、输入、输出是表单；脚本是内置代码编辑区（行号、着色、查找）。
   - 右边：**测试运行**，和启动器用同一个运行器，预览区就是启动器里的卡片。
3. **表单和 `workflow.json` 双向同步**（截图 2、5）。表单只改它认识的字段，清单里的其他字段原样保留；JSON 视图把校验错误标到对应的行。
4. **出错直接定位到行**（截图 4）。从 stderr 里识别「文件 + 行号」，标在代码上；启动器的错误卡片加 **⌘E 编辑工作流**，直接打开编辑器到出错的那一行。
5. **信任不打折扣**（截图 6）。在编辑器里保存会自动更新信任，前提是这段时间里没有别人改过文件；只要有外部修改，就必须先看差异、确认信任。编辑器不能变成绕过信任的后门。
6. **AI 助手**（截图 ⑩–⑫，第 10 节）。一句话描述就能**一键生成**工作流：AI 通过 Ask 的 agent 写清单和脚本、在本机试跑、失败自己改；编辑器里可以**对话修改**，测试失败可以**让 AI 修复**。AI 只能提交「修改提案」，用户看过差异再应用和保存；试跑前做风险检查，出现新的网络地址、删除文件、读敏感位置等情况时停下来问。
7. **不加新依赖。** 代码区用 `NSTextView` 加一个轻量的着色器，查找用系统自带的查找栏。
8. **分三步做。** E1：编辑器本身。E2：AI 助手（生成、修改、修复）。E3 跟着 W2：条目列表的预览、边打边出、钥匙串密钥、运行记录面板。

## 1. 用户怎么用

### 1.1 改一个已有的工作流

设置 → Agent → 内置工具 →「启动器工作流」，点一行的「编辑」，打开编辑器。

1. 在流程条上点「脚本」，改代码；文件标签上出现未保存的圆点。
2. 在右侧输入 `100 usd jpy`，按 ⌘R：先保存，再运行，右侧显示启动器里的样子。
3. 出错时，出错的行标红，stderr 里的 `main.py, line 12` 可以点。改完再 ⌘R。
4. 关掉窗口。保存过的修改立即生效，不需要再确认信任。

### 1.2 新建一个工作流

「＋ 新建」→ 默认是「用 AI 生成」：写一句「输入 `fx 100 usd jpy` 时查实时汇率换算」→「生成」→ AI 写好并试跑 → 在编辑器里看一眼 →「检查并保存」（截图 10，第 10 节）。

也可以选模板（Python / Node / zsh 输出文本，zsh 只做事，空白，复制现有）→ 填名称和关键字（实时查重）→「创建并编辑」（截图 7）。

### 1.3 在启动器里遇到错误

工作流出错时，错误卡片显示 stderr 末尾和 **⌘E 编辑工作流**。按 ⌘E，启动器关闭，编辑器打开到这个工作流、出错的那一行（截图 8）。也可以点「让 AI 修复」：编辑器打开后 AI 直接开始修（截图 12）。

## 2. 窗口结构

```
┌ 工具栏：图标 名称 id·版本 [运行时] [状态]        未保存· [保存 ⌘S] [▶ 测试运行 ⌘R] ··· [开关] ┐
├────────────┬────────────────────────────────────────────┬─────────────────┤
│ 搜索        │ 流程条：[关键字] → [输入] → [脚本] → [输出]         │ 测试运行          │
│ 工作流列表   ├────────────────────────────────────────────┤ 输入 / 示例选中文字 │
│  └ 文件     │ 标签：表单 | workflow.json  或  main.py | …      │ 预览 stdout stderr │
│            │ 编辑区                                       │ 传入了什么        │
│ ＋新建 导入  ├────────────────────────────────────────────┤ 最近运行          │
│            │ 状态栏：问题 · 解释器 · 行列 · 编码              │                 │
└────────────┴────────────────────────────────────────────┴─────────────────┘
```

- **单独的窗口**，只有一个实例；从任何入口打开都复用它，切到对应的工作流。默认 1220×700，最小 960×560；右侧测试面板可以收起（⌥⌘T）。
- **左栏**：全部工作流（状态点：绿=可以运行，黄=需要确认，红=清单有误，灰=已停用），选中的展开文件列表：「配置」（`workflow.json`）、脚本、其他文本文件。二进制文件（图标）只显示不打开。
- **工具栏**：名称、`id · 版本`、运行时、状态；保存、测试运行、更多（在 Finder 中显示、用外部编辑器打开、复制、删除）、启用开关。
- **状态栏**：问题数（点击跳到第一个问题）、解释器路径、光标位置、编码和缩进。
- 切换工作流或关窗口时有未保存的修改，弹出「保存 / 不保存 / 取消」。

## 3. 流程条和各步骤

流程条就是工作流做的四件事。每个节点显示摘要，选中的节点高亮，对应的校验问题让节点带红点（问题按字段前缀归到步骤：`keywords*` → 关键字，`input*` → 输入，`command*` → 脚本，`output`/`run*`/`env` → 输出）。

| 步骤 | 摘要 | 编辑区 |
|---|---|---|
| 关键字 | 关键字标签 + 第一个显示名称 | 表格：关键字、显示名称、预设参数（键值对），可增删、拖动排序。输入时就查重（和内置插件、其他工作流同一个命名空间，复用 `AskKeywordMatcher.problem` 和 `AskWorkflowStore.keywords(of:excluding:)`），错误写在那一行下面。 |
| 输入 | 「可选 · 或选中文字」 | 参数：必填 / 可选 / 不需要；选中的文字：没参数时用 / 总是带上 / 不要；**参数模板**：一格一个 argv，占位符 `{query}` `{selection}` `{option:名字}` 点一下插入，名字从关键字表的预设参数里取。下面实时显示示例的 argv 和 stdin JSON（复用 `AskWorkflowManifest.arguments` 和 `AskWorkflowPlugin.stdin`）。 |
| 脚本 | `main.py {query}` | 代码区（第 4 节）。脚本 / 内联脚本切换（只有 zsh、bash 可以内联）。 |
| 输出 | 「文本 · 10 秒」 | 输出：文本 / 不输出 / 自动 / 条目列表（W2）；运行：按 ↩ / 边打边出（W2）；超时（1–300 秒）；运行时和解释器（自动找到的路径以占位文字显示，找不到时提示怎么安装）；环境变量表。右边按当前选择渲染启动器预览。 |

W2 才支持的选项（条目列表、边打边出）显示为不可选并标「W2」，和现有校验一致。

## 4. 代码区

- `NSTextView`（TextKit 1，`NSScrollView` + 行号 `NSRulerView`），等宽字体，关闭智能引号、自动替换、拼写检查，`isRichText = false`。
- **着色**：每种运行时一组正则（注释、字符串、关键字、数字、函数调用），只给可见范围和编辑过的段落重新着色；超过 2,000 行或 256 KB 时只着色可见范围。语言按运行时和扩展名决定（`.py` `.js/.mjs` `.ts` `.sh/.zsh` `.applescript/.scpt` 文本、`.json`）。不引入 tree-sitter 等依赖。
- **编辑**：Tab 插入 4 个空格（按文件里已有的缩进自动判断 2 或 4），回车保持缩进，⌘/ 注释，撤销重做，⌘F 用系统查找栏（`usesFindBar`）。
- **问题标记**：行号栏的红点 + 该行下方一行说明（截图 4、5），来源有两个：清单校验（只在 `workflow.json` 里）和最近一次测试运行的 stderr。
- 只打开 UTF-8 文本文件，最大 1 MB；更大或不是 UTF-8 的文件提示「用外部编辑器打开」。
- 「用外部编辑器打开」保留，仍然用纯文本编辑器打开（不会误运行脚本）。

## 5. 表单和 `workflow.json` 同步

- 编辑器持有一份**草稿**：清单的原始 JSON 对象（`[String: Any]`，保留全部字段）+ 由它解码出的 `AskWorkflowManifest`。
- 表单修改时，只改原始对象里对应的键，再重新解码、校验；所以清单里表单不认识的字段（作者自己加的 `x-roots`、以后的新字段）不会丢。写出时用排序键、两空格缩进，和模板一致。
- JSON 视图修改时（停顿 300 ms 后）解析：能解析就刷新表单；解析不了时只标语法错误位置，表单变为只读，直到 JSON 恢复正确。
- 校验复用 `AskWorkflowManifest.problems(in:)`，再加上 JSON 解码错误（`AskWorkflow.describe`）。每个问题带字段路径，JSON 视图用路径找到对应的行（简单的键路径扫描，不需要完整的 JSON 位置解析器）。
- 能猜到的给一键修正：`command.script` 找不到时，列出文件夹里同扩展名或同运行时的文件。

## 6. 保存、信任和外部修改

这是本方案里最需要小心的部分：编辑器会写文件，也会更新信任。

### 6.1 保存

- ⌘S 保存全部修改过的文件；每个文件先写临时文件再原子替换（`replaceItemAt`），脚本保留原来的权限，新建的脚本设为 `0755`。
- **有校验问题也允许保存**：写了一半的工作流在启动器里显示「清单有误」，和今天一致。
- 保存后重新计算内容哈希，刷新 `AskWorkflowStore`。

### 6.2 保存时什么时候更新信任

编辑器打开一个工作流时，记录**载入时的哈希** `H0` 和它当时的状态。保存时：

| 情况 | 结果 |
|---|---|
| 载入时是「可以运行」，并且保存前磁盘上的哈希仍然是 `H0` | 写入，记录新哈希为已信任。用户自己改的，不需要再确认。 |
| 载入时是「已停用」，同上 | 写入，更新信任，仍保持停用。 |
| 载入时是「未信任」或「已修改」 | 写入，**不**更新信任。工具栏仍显示「检查并信任…」。 |
| 保存前磁盘上的哈希已经不是 `H0`（编辑器外有人改过） | 不写入，出现外部修改横幅（6.3）。 |

「检查前后哈希 + 写入 + 记录信任」在主线程上一次完成，中间不让出；写入后立刻重新计算哈希，记录的是磁盘上真实的哈希，而不是我们以为写进去的内容。

### 6.3 外部修改

- 编辑器监听当前工作流文件夹（每 2 秒在后台重新计算一次哈希；文件夹很小，开销可以忽略，也不会漏掉编辑器原子保存产生的改名）。
- **没有未保存的修改**：外部改动直接载入。如果工作流原来是「可以运行」，现在会变成「已修改」——编辑器里出现横幅，和启动器一样，确认信任前不能运行。
- **有未保存的修改**：横幅「main.py 在编辑器外被修改了」，三个选择（截图 6）：
  - 「查看差异并信任…」：逐文件显示差异（我的版本 / 差异 / 外部版本），确认后走现有的信任面板。
  - 「载入外部版本」：丢掉自己的修改。
  - 「保留我的版本」：覆盖外部改动；保存后**不**自动信任，因为外部改动可能已经被运行过或者还在别的文件里——工作流保持「已修改」，需要用户点信任。
- 测试运行和启动器一样先检查信任：不是「可以运行」时，测试按钮不可用，提示「先检查并信任」。

## 7. 测试运行

- **⌘R 先保存再运行**。这样测试的就是磁盘上的那一份，和启动器完全一致，信任检查也不需要特殊处理。
- 输入：关键字（多个关键字时可以选，用于带上预设参数）、参数、可选的「示例选中文字」、可选的「来源 App」（默认 Typeflux 自己）。
- 运行：直接调 `AskWorkflowPlugin` 的同一套路径（`input(for:)`、`invocation`、`environment`、`AskWorkflowRunner`），所以超时、输出上限、干净环境、取消时结束进程组全部一样。stdin 里的 `reason` 用 `submit`，脚本看不出是测试——我们希望行为一致。
- 结果标签：
  - **预览**：按清单的输出类型渲染启动器卡片（文本 / 「启动器会关闭」/ 错误卡片）。
  - **stdout**、**stderr**：原样，stderr 里识别出的位置可以点。
  - **传入了什么**：实际的 argv、环境变量（只列 `TYPEFLUX_*` 和清单的 `env`；密钥打码）和 stdin JSON。
- 运行中按钮变成「停止」（⌘.）；运行中再按 ⌘R 会先结束上一次。
- 测试运行也写进 `AskWorkflowLog`（标记来源是测试），「最近运行」里能看到启动器和测试两种。日志仍然**不记录输入输出**；测试面板里显示的输出只在内存里，关窗口就没了。

### 7.1 从 stderr 找行号

只认指向**工作流文件夹里的文件**的位置，避免把第三方库的堆栈标到用户的代码上：

| 运行时 | 格式 |
|---|---|
| Python | `File "…/main.py", line 12` |
| Node / TypeScript | `…/main.js:12:5`、`at … (…/index.ts:12:5)` |
| zsh / bash | `main.sh:12:`、`main.sh: line 12:` |
| osascript | `main.applescript: 1:20: execution error` |

取最后一个匹配的位置（最靠近出错点），在那一行下面显示 stderr 的最后一行。

## 8. 入口

- **设置列表**：每行加「编辑」按钮；清单有误时变成「修复…」，打开后跳到第一个问题。「用外部编辑器打开」移到 ··· 菜单。列表底部加「打开工作流编辑器」。
- **新建**：「＋ 新建工作流…」打开编辑器并弹出新建面板。
- **启动器**：工作流的结果卡片支持 ⌘E（成功时也可以用）：关闭启动器，打开编辑器到这个工作流；出错时直接到出错的行。快捷键说明写在卡片按钮和底栏里。
- 不放进菜单栏菜单，避免增加一个很少用到的入口。

## 9. 新建工作流

- 模板：现有的 4 个（`AskWorkflowTemplate`）+「空白」（只有清单，运行时和脚本自己选）+「复制现有工作流」（复制文件夹，id 和关键字自动加后缀）。
- 先填**名称**和**关键字**（实时查重）；ID 由名称生成（`local.` + 名称转成的 slug：中文用系统的 `CFStringTransform` 转拼音，转不出时用模板 slug），可以手改，用 `AskWorkflowManifest.isValidID` 校验。
- 创建后视为已信任（和今天一样，用户自己创建的），直接进入编辑器的「脚本」步骤。
- 导入文件夹 / `.typefluxworkflow` 也从这里进入（导入属于 W3）；导入的工作流先走信任面板，再进编辑器。

## 10. AI 助手

目标：大多数工作流不需要用户自己写。用户用一句话说要什么，AI 通过 Ask 的 agent 写好清单和脚本、在本机试跑、出错自己改；用户只负责看结果、点保存。AI 写的东西和手写的走同一条路：先进草稿，用户确认后保存，信任规则不变。

### 10.1 三个用法

| 用法 | 入口 | 截图 |
|---|---|---|
| **一键生成** | 「新建工作流」面板的第一个选项「用 AI 生成」：写一句描述（可以带例子），选语言（默认自动）、关键字（AI 建议，本地查重），点「生成」。 | ⑩ |
| **对话修改** | 编辑器右侧面板的「AI 助手」标签（和「测试运行」并列）：「再加一个 rate 关键字」「结果保留两位小数」「改成用 Node 写」。 | ⑪ |
| **让 AI 修复** | 测试运行失败时测试面板里的按钮；启动器错误卡片里的「让 AI 修复」（打开编辑器，把这次的输入、stderr 和出错的行交给 AI）。 | ⑫ |

### 10.2 一键生成的过程

1. **理解需求**：整理出输入（参数、要不要选中文字）、输出（文本 / 只做事）、建议的关键字和运行时。描述不清楚时只问一个问题，不连环追问。
2. **检查本机环境**：有哪些解释器和版本、描述里用到的命令（如 `pandoc`）在不在；缺第三方库时优先改用标准库。
3. **写清单和文件**：`workflow.json`、脚本、简短的 `README.md`（用法和例子）。
4. **试跑**（「生成后自动试跑」默认勾选）：AI 自己想 2–5 个例子（包括一个出错的例子），在本机跑；失败就改，**最多 3 轮**。
5. 完成后进入编辑器：右侧是这次生成的提案和试跑结果，中间可以看代码；用户点「检查并保存」才写进工作流目录。

生成和试跑都在**暂存区**（`~/Library/Caches/Typeflux/WorkflowDrafts/<uuid>/`）进行；保存前它不在工作流目录里，启动器看不到，取消就删掉。

### 10.3 AI 怎么改：修改提案

AI 不直接改用户的文件，每次改动都是一个**修改提案**（截图 ⑪）：

- 改了哪些文件、各多少行；说明；是否已经试跑以及结果。
- **风险标签**（10.5）：访问哪些网络地址、是否写 / 删文件、是否启动其他程序、是否读敏感位置。和当前版本相比**新出现**的用黄色标出。
- 操作：「查看差异」（中间显示逐行差异，和外部修改用同一个差异视图）、「放弃」、「应用」。
- 「应用」只改编辑器里的草稿（顶部横幅可以「撤销」），之后照常 ⌘S 保存——手改和 AI 改走完全相同的保存和信任规则（第 6 节）。
- 新建时的「检查并保存」= 应用 + 保存：把暂存区移进工作流目录，记录为已信任。因为这是用户自己让 AI 写、看过提案后点的保存，和用模板创建一样对待；但如果提案带有高风险标签（10.5 的最后三类），保存前要再勾选一次「我已看过这些操作」。

### 10.4 AI 能用的工具

助手是一个专用的 Ask 会话。客户端只提供下面这几个工具，其他本地工具（文件、电脑、浏览器、MCP、`run_code`、记忆）都不提供，范围越小越可控。云端会话里，服务端自己的 `web_search` / `web_fetch` 和计划工具总是存在（`typeflux-api` 的 `internal/ask/cloud.go` 每次运行都会加上，客户端关不掉）。这反而有用：AI 可以查 API 文档。查到的内容和其他工具结果一样只当数据，它也只能通过下面的工具产生效果。

| 工具 | 风险级别 | 做什么 |
|---|---|---|
| `workflow_read` | 读 | 读当前工作流（或暂存区）的清单、文件列表、文件内容，以及校验问题和上次测试结果。只能读这一个工作流。 |
| `workflow_environment` | 读 | 已找到的解释器和版本（Typeflux 自己用 `--version` 取一次并缓存）；给一组命令名，返回在 PATH 上的路径或「没有」。只做查找，不运行这些命令。 |
| `workflow_check_keyword` | 读 | 关键字能不能用（和内置插件、其他工作流查重）。只返回能 / 不能和冲突的名字，不返回其他工作流的内容。 |
| `workflow_propose` | 写暂存区 | 提交一个修改提案：完整清单、要写的文件（路径 + 内容）、要删的文件、说明。本地校验：路径必须在工作流文件夹里（复用 `AskWorkflowManifest.scriptURL` 的规则）、最多 20 个文本文件、每个 ≤ 256 KB；清单的校验问题原样返回给 AI，让它自己改。 |
| `workflow_test` | 运行 | 用最多 5 组输入（参数、可选的示例选中文字、关键字）试跑**最新的提案**，返回退出码、耗时、stdout / stderr（各截到 4 KB）。在提案的暂存副本里运行，不碰用户的文件；运行器、干净环境、超时、输出上限和测试运行完全一样。受 10.5 的规则约束。 |

工作流的写法（清单字段、输入输出约定、各运行时的规则、「参数是独立的 argv」「出错时打印 `{"error": …}`」「不要把密钥写进清单」等）作为内置技能 `typeflux-workflow-author`，用现有的 `AskSendRequest.skills`（`AskSkillUse`）随每次请求发送。云端会话由服务端放进提示词（`internal/ask/choices.go`），本机私有会话由 `AskLocalPrompt.choices` 放进去——两条路都已经存在。服务端限制每个技能说明最多 40,000 个字符，作者技能要控制在这个范围内（预计 6–8 千字）。

### 10.5 安全：试跑前的风险检查

AI 写的代码会在用户的 Mac 上试跑，而且可能在用户读代码之前。约束如下：

- **静态风险检查**：每个提案都按运行时做一次规则扫描，得到风险标签：
  - 网络：代码里出现的主机名（URL、`urlopen`、`fetch`、`curl` 等）；
  - 写文件（工作流数据 / 缓存目录、临时目录以外）；
  - 启动其他程序（`subprocess`、`child_process`、`os.system`；shell 脚本列出用到的外部命令）；
  - **删除**（`rm`、`unlink`、`rmtree`…）；
  - **敏感位置**（`~/.ssh`、`~/.aws`、钥匙串、`security find-generic-password`、浏览器配置目录）；
  - **提权或下载即执行**（`sudo`、`curl … | sh`、`eval` 下载的内容）。
- **什么时候自动试跑，什么时候停下来问**：
  - 一键生成的第一版：没有后三类高风险标签时自动试跑；有就暂停，等用户看过再继续。
  - 之后的每一版（自动修复、对话修改）：和**用户上次认可的版本**相比没有新的风险标签时自动试跑；有任何新标签（例如新的网络地址）就暂停（截图 ⑫），用户可以「允许并继续」「只用前一个提案」或看差异。
  - 用户关掉「生成后自动试跑」时，每次试跑都要点一下。
- 静态扫描是**提醒，不是安全边界**：能被绕过，所以真正的边界仍然是「保存前用户确认」+ 运行器的限制（干净环境、不带密钥、超时、输出上限、结束整个进程组）。W3 的受限运行（`sandbox-exec`）做好以后，AI 的试跑默认用它：只允许写暂存目录和临时目录。
- **不发给模型的东西**：密钥的值、钥匙串、其他工作流的代码、启动器的运行记录（本来就不记输入输出）。**会发给模型的**：当前工作流的文件、用户在测试里输入的内容（包括示例选中文字）、试跑的输出。这一点写在 AI 助手面板的空状态里。
- **提示注入**：脚本输出、stderr、文件内容都作为数据交给模型（和现有本地提示词一样声明「是数据不是指令」）。即使模型被诱导，它能做的也只有：改暂存区里的提案、在 10.5 的规则下试跑——不能保存、不能信任、不能碰其他工作流。
- **用量**：每条消息最多 3 轮自动修复、最多 10 次试跑；随时可以停。用量计入 Ask。

### 10.6 用哪个 agent、会话存在哪

- 走 Ask 的现有通路（`AskConversationModel`）：登录了 Typeflux Cloud 就用云端会话，否则（或用户选了私有会话）用本机配置的模型。模型选择器和 Ask 一样。
- 每个工作流一个助手会话，记在 Ask 历史里，标题「工作流：汇率换算」；编辑器打开这个工作流时接着上次的会话。新建时的生成会话在保存后归到新工作流名下，取消则删除。
- **服务端不用改**：已核对 `typeflux-api` 的 `validateTools`，客户端工具只校验名字格式（`^[A-Za-z0-9_-]{1,64}$`）、不能和 `web_search` / `web_fetch` 等服务端工具重名、最多 64 个、schema 合计不超过 500 KB，没有白名单；10.4 的五个工具名都符合。

## 12. 测试

- **草稿**：按键路径修改不丢未知字段；表单 ↔ JSON 往返一致；JSON 语法错误时表单只读；字段路径归到正确的步骤。
- **保存和信任**（第 6.2 节每一行一个用例）：可以运行 → 保存后仍然可以运行；未信任 / 已修改 → 保存后仍然需要确认；保存前文件被外部改过 → 不写入、报告冲突；「保留我的版本」覆盖后不自动信任；写入后记录的是磁盘上的真实哈希。
- **原子写入**：保留脚本权限；写入失败时原文件不变。
- **外部修改**：无未保存修改时自动载入；有未保存修改时进入冲突状态。
- **测试运行**（真实进程，用仓库内的夹具脚本）：和启动器同样的 argv / 环境 / stdin；超时和停止后没有残留进程；不信任时不能运行；密钥在「传入了什么」里打码；日志不含输入输出。
- **行号识别**：四种运行时的格式；只认工作流文件夹里的文件；多个匹配取最后一个。
- **着色器**：每种语言的注释、字符串（包括转义引号和多行字符串）、关键字；大文件只处理给定范围。
- **新建**：名称生成 ID、关键字查重、复制工作流加后缀。
- **AI 工具**：`workflow_propose` 拒绝文件夹外的路径（`..`、绝对路径、符号链接）、超量文件和非文本内容，清单问题原样返回；`workflow_read` 读不到其他工作流；`workflow_check_keyword` 不泄露其他工作流内容；`workflow_test` 在暂存副本里运行、不改用户文件、结果截断。
- **风险扫描**：每类标签的正例和反例（注释里的 URL、字符串里的 `rm` 不误报的常见情况）；`newRisks(since:)` 只报新增的。
- **自动修复的暂停规则**：首版有高风险时不试跑；之后的版本出现新标签时暂停；轮数和试跑次数上限；用户停止后不再发起工具调用。
- **提案**：应用后草稿和提案一致、可撤销；新建时「检查并保存」把暂存区移进工作流目录并记录信任；高风险提案保存前必须勾选确认；取消后暂存区被删除。
- **会话**：用假的 `AskAPI` 走一遍「生成 → 试跑失败 → 修复 → 通过 → 保存」，确认请求里只有 10.4 的工具和作者技能、没有密钥。
- **界面**：截图测试覆盖设计稿的各个状态；启动器错误卡片 ⌘E 打开编辑器并定位到行。
- 新代码覆盖率 ≥ 90%。

## 14. 需要你确认

1. **保持「一个工作流 = 一个脚本」**，流程条只是把它的四个环节可视化。还是希望做成 Alfred 那样的**多节点连线**（一个工作流里串多个脚本、条件分支）？我建议先不做：现有清单、运行器、信任都是按单脚本设计的，多节点会让格式和安全模型都复杂很多；串联需求可以先在一个脚本里完成。
2. **独立窗口**，而不是在设置页里展开。设置窗口太窄，放不下代码和测试面板。
3. **⌘R 先保存再运行**。另一种做法是把草稿复制到临时目录去跑，不碰原文件；但那样测试的不是启动器会运行的那一份，信任检查也要另做一套。
4. **代码区用 `NSTextView` + 正则着色**，不引入 tree-sitter 或在 WebView 里放 Monaco。够用、没有新依赖、包体不变；代价是着色不如真正的语法分析准确，复杂编辑仍然建议用外部编辑器。
5. **在编辑器里保存自动更新信任**（第 6.2 节的条件）。这是解决「改自己的工作流还要反复确认」的关键，同时保证外部改动一定要人看过。
6. **AI 生成后自动试跑默认打开**，靠风险扫描在高风险时暂停（第 10.5 节）。更保守的做法是每次试跑都要点一下；我建议默认打开，否则「一键生成」就变成了好几键。
7. **AI 生成的工作流点「检查并保存」后直接信任**，和用模板创建一样；只有带高风险标签时多勾选一次确认。
8. **客户端只给助手 10.4 的五个工具**，不给文件、MCP 等；云端会话里服务端的网页搜索照常可用（用来查 API 文档）。如果你希望助手完全不联网，需要在服务端加一个按会话关闭网页工具的开关（小改动），本机私有会话则天然没有网页工具。

## 15. 实现说明（E1 + E2）

**代码位置**
- 模型（`Ask/QuickResults/Plugins/Workflow/Editor/`）：
  - `AskWorkflowDraft`：`workflow.json` 以文本保存，`set(_:at:)` 按键路径修改并保留未知字段；按字段路径找行、归到流程步骤；草稿里才有的脚本算作存在。
  - `AskWorkflowStore+Editor`：第 6.2 节的保存规则（只有载入时的版本是已信任、且磁盘上仍是载入时的哈希，保存后才继续信任；`expectedHash` 为 nil 的「保留我的版本」永远不授予信任）、原子写入和权限、改 id 时迁移信任和开关、按名称新建（中文名转拼音做 id）、复制、把生成的工作流从暂存区装进来。
  - `AskWorkflowTester`：用 `AskWorkflowPlugin` 生成同样的命令、环境和 stdin，用同一个运行器跑；结果带 argv、环境（不含 HOME、PATH 等基础变量）和 stdin，记录写入运行日志（来源标为测试）。
  - `AskWorkflowStderrLocator`、`AskWorkflowSyntaxHighlighter`、`AskWorkflowRiskScanner`：纯函数。
  - `AskWorkflowProposal`、`AskWorkflowDiff`、`AskWorkflowStaging`：提案、逐行差异、暂存目录（启动编辑器时清理一天以前的残留）。
  - `AskWorkflowAuthorTools`、`AskWorkflowAuthorSkill`、`AskWorkflowEnvironmentProbe`：第 10.4 节的五个工具和作者技能。
  - `AskWorkflowAssistant`：直接驱动 Ask 的 `AskAPI`（和 Ask 窗口共用 `AskRoutedAPI`、会话、设备 id 和模型库，由 `DIContainer` 注入），处理 `waiting_tool`（只执行五个工具）和 `waiting_inference`（本机模型），每条消息最多 40 次工具调用；会话按工作流 id 记在 `ask.workflows.assistant`。
  - `AskWorkflowEditorModel`：打开、编辑、保存、外部修改（轮询）、测试运行、新建 / 生成、提案的应用 / 放弃 / 撤销，以及试跑前的风险审批。
- 界面（`Settings/WorkflowEditor/`）：窗口控制器（单实例）、编辑器主视图、侧栏、流程条、三个表单、代码区（`NSTextView` + 行号标尺 + 着色）、差异视图、测试面板、助手面板、新建面板。
- 入口：设置列表的「编辑」「修复…」和「工作流编辑器」按钮，「新建工作流」菜单里的「用 AI 生成」；启动器里工作流出错时卡片上有「编辑工作流 ⌘E」和「让 AI 修复」，成功的结果也可以按 ⌘E。

**和设计的差别**
- 外部修改用轮询而不是 `DispatchSource`（见第 6.3 节）。
- 应用提案后的撤销是横幅上的按钮，没有接入代码区的 ⌘Z 撤销栈。
- 「空白」模板没有做：「从模板」里是现有的四个模板，另有「复制」和「用 AI 生成」。
- 编辑器打开外部请求（设置、启动器）时，如果有未保存的修改：同一个工作流只跳到对应行，其他工作流提示先保存或放弃，从不替用户保存或丢弃。

- 草稿：按键路径修改保留未知字段、JSON 写坏时表单只读、问题归到步骤和行。

## 17. 简化（第三轮）

真实生成一次之后，界面显得太复杂：生成面板压在完整的编辑器上，两处显示同一份进度；每个工具步骤占一行；技术细节（运行时、快捷键文字、编码缩进、解释器路径、上下文标签、隐私说明）铺满界面。这一轮只减少默认露出的东西，功能都还在。

**用 AI 新建**
- 默认只有描述框和示例；关键字、语言收进「选项」。不填关键字时，AI 自己挑一个并用 `workflow_check_keyword` 确认可用（对话里只显示用户写的描述）。
- 生成中：一行进度（最近一步 · 第 N 版 · 试跑 a/b 通过），步骤收进「N 个步骤」。需要允许试跑时，直接在面板里回答。
- 完成后：「X 做好了」、在启动器里输入什么、试跑结果的启动器预览、实际存在的风险；「保存」直接装进启动器，「在编辑器里调整」进入编辑器。

**编辑器**
- 顶栏：名称、未保存标记、保存、测试、「···」、开关。徽标只在出问题时出现；快捷键放到悬停提示里。生成中的工作流只有一个「保存」。
- 去掉「由助手生成」「已应用提案」两条横幅；撤销移到提案卡片上，撤销后的提案可以再次应用。
- 侧栏只列工作流；文件是代码上方的标签页，「+」添加，右键删除。
- 代码区顶部不再放「查找 / 外部编辑器」文字按钮（⌘F 可用，外部编辑器在「···」）。脚本步骤显示「运行时 · 文件」，解释器版本在悬停提示里。
- 状态栏只在有问题、试跑失败或外部修改时出现。
- 助手：连续工具步骤合成一行（可展开）；输入框下只留模型名，隐私说明在 ⓘ 提示里；「自动试跑」在「···」菜单里；提案卡片只列实际风险。
- 测试面板去掉标题行和「和启动器同一个运行器」徽标；审批卡片的说明放进悬停提示。

**顺带修复**：代码变短后（例如撤销提案），如果光标在新的末尾之后，`NSTextView` 会收到空的选区并抛异常；现在改成落在末尾。
